## Ruling [124] — no repository method

`buildScheduleRange` takes `readonly PlanRecord[]` — whatever `listPlans` released for the actor —
and does the rest itself. It calls no store. `listSendableContacts` is neither called nor changed.

**Where the derivation lives, and why.** The sealed domain, `src/lib/caring-contacts/`. Three of the
four rules it composes are already owned there — the window mapping (`./schedule`), the sendability
classification (`./model`), the plan lifecycle — and the fourth, that a plan's own state holds
sending, is a rule about the domain rather than about any screen. There will also be more than one
reader: this HTTP route publishes it, and Task 13's Server Component render will read the store
directly rather than call the service over its own network, exactly as `patients/page.tsx` does
beside `plans/route.ts`. Both readers must get the same answer, and the only way to guarantee that is
for there to be one answer. The argument is written into the module header.

## What the read answers

`buildScheduleRange(plans, fromCalendarDay, toCalendarDay)` returns
`{ ok: true; view } | { ok: false; reason }`. The view holds every day of the inclusive range, in
order, **including the days holding nothing** — the seven-day strip and the selected day come from
one call. A single day is the range `(day, day)`; there is deliberately no second entry point,
because two entry points would be two places for the grouping to be applied slightly differently.

Each `ScheduleDay` holds:

- **`windows`** — always all three approved windows, in the order they occur in a day, taken from
  `SENDING_PREFERENCE_OPTIONS` so neither the order nor the wording is restated here.
- **`outsideApprovedWindows`** — see "What Task 13 has to render that the mockup does not show".
- **`exceptions`** — the named-exceptions panel's contents.
- **`counts`** and **`disposition`**.

Each `ScheduleEntry` carries the plan, patient and contact identifiers, the cadence label, the
message type, the AWST day and instant it sends at, and four derived facts:

| Field              | What it says                                                                     |
| ------------------ | -------------------------------------------------------------------------------- |
| `sendability`      | `contactSendability(state)`, unmodified — the contact's own answer.              |
| `planHold`         | What the PLAN's state says: `planNotStarted`, `planPaused`, `planEnded`, null.   |
| `isDue`            | Still to send AND not held. The only entries the service will actually send.     |
| `notSendingReason` | `absorbedByFirstContact`, `suppressed`, `cancelled` or `missed`; otherwise null. |

## The plan-state gate

The filed defect on `listSendableContacts` is that it has none. This read has one, and it is not a
workaround for that surface — it is the rule stated where a schedule needs it. Neither `pausePlan`
nor `activatePlan` touches a contact, so a draft plan's contacts and a paused plan's contacts both
sit in `scheduled`. A read that asked only the contact would announce a plan nobody has started, and
a plan a coordinator deliberately paused, as work the service is about to do.

`planSendingHold` is an exhaustive switch over `PlanState` rather than a list of held states, so a
seventh plan state cannot default into "this plan is sending".

## Counts are derived

`ScheduleCounts` is `StoredContactSummary & { due, held, needsReview }`. The sent / still-to-send /
never-will arithmetic is `summariseStoredContacts`'s, unchanged and not re-implemented; what this
read adds is the split of `stillToSend` into the part the service will send and the part its own plan
is holding. The invariant is stated on the type and asserted in the suite:
**`due + held === stillToSend`**.

Nothing in the code or in this report states how many contacts a plan has. The absorbed-contact case
is asserted by deriving both sides from the plan under test: the entries carrying
`absorbedByFirstContact` must equal the planned entries the planner marked suppressed, and the due
entries must equal the day's entries less those.

## The empty-state distinction, one layer down

`ScheduleDayDisposition` has three values, and the first two are the ones that matter:

- `noContactsPlanned` — no contact falls on this day at all.
- `nothingDue` — contacts fall on this day and none of them is due.
- `contactsDue` — at least one is.

A day whose every contact was cancelled by a withdrawal reports `nothingDue` with
`counts.willNotBeSent` equal to `counts.total` and each entry naming `cancelled`; a day that was
never given a contact reports `noContactsPlanned` with a total of zero. An absorbed first contact
reports `absorbedByFirstContact`, which is the plan working as designed, and is kept apart from a
cancellation, which means something stopped it. All three are asserted.

## Ruling [125] — the trail

The read is recorded as `{ search, contactSchedule, "<from>:<to>" }`. Its own `AccessedObjectType`
member rather than the caseload's `plan`: recording it as `plan` would be defensible by provenance
and wrong by meaning, and with no `objectId` filter on the trail's query surface a shared member
would make a caseload read and a schedule read one undifferentiated stream. The `objectId` is the two
days that were read — identifier-shaped by construction, because the schema accepted only two AWST
calendar days before either could reach it.

`src/app/api/caring-contacts/access-trail/route.ts`'s `z.enum` is a hand copy of that union and
nothing in the build compared the two. `tests/caring-contacts-schedule-route.test.ts` now pins them
as the same set, in the same order, by parsing both files; every step of that parse throws rather
than comparing two empty lists. That closes the mechanism the filed issue describes, as a side effect
of this task — flagged rather than claimed, because the issue is not mine to close and a maintainer
should decide whether this pin is where the check belongs.

## What Task 13 gets

A `ScheduleRangeView` per call, either from `GET /api/caring-contacts/schedule?from=&to=` or — the
shape the other workspace screens use — by calling `buildScheduleRange` on an `auditedRead` of
`listPlans` inside the Server Component, with the same access identity the route records. It gets,
per day: the three windows with their approved wording and send times; a fourth group for contacts
moved off an approved send time; the named exceptions; the counts; and the disposition. Every entry
carries its own state, its plan's hold, whether it is due, and why it is not.

It releases **no patient identity**: `PlanRecord` carries none, so a row is keyed by the synthetic
`patientId` and a screen wanting names reads `listPatientNames`, which is audited in its own right.
That is asserted at both layers.

### What Task 13 has to render that the mockup does not show

**A contact can be scheduled at a time that is not one of the three approved send times.**
`moveContactWithinDay` accepts any hour and minute inside the approved 09:00–18:00 window and both
stores persist it, so 11:30 is an ordinary stored state. Nothing in this domain says which window a
moved contact then belongs to, and inventing a band (09:00–11:59 is "morning") would be a second copy
of the window mapping and a rule nobody approved. So `sendingPreferenceAt` matches the approved hour
**and** minute, and a contact matching neither is reported in `outsideApprovedWindows` rather than
filed under a window it has left. The approved design shows three window columns and no fourth group.
**This is a difference between the design and the types, recorded rather than resolved**; the owner
should say what that group is called on screen.

**A held contact is not an exception.** A draft plan whose first contact day has arrived, and a
paused plan's contacts, are reported as `held` and are not put in the named-exceptions panel. That is
a judgement, not a derivation: the approved design's exception panel is about transport, and adding
an operational category to it is a product decision. Task 13 has `counts.held` and each entry's
`planHold` if the owner wants them surfaced.

**Named exceptions** are the four provider outcomes that are not a delivery, plus `missed` — five
contact states, classified by an exhaustive switch so a new state cannot default into "not an
exception". They are taken OUT of their sending window rather than listed twice, because the design
keeps named exceptions separate from the routine window lists and a screen rendering both would
otherwise count one patient as two. The invariant is asserted: **every entry a day holds appears in
exactly one group.**

## Verification

### Boundary cases, written first

**The 00:00 case is the timezone guard. The 17:00 case is not, and this section originally let a
reader think otherwise** — corrected in the fix round below rather than left to be inherited.

- **00:00 AWST — the timezone guard.** 2026-09-01 00:00 AWST is 2026-08-31 16:00 UTC. Unreachable
  through `buildApprovedSchedule` — the approved window starts at 09:00 — so this record is assembled
  by hand and labelled defensive, with `planned.calendarDay` deliberately set to the UTC date. **All
  three answers are therefore available to the code and only one is right**: it must place the
  contact on the AWST day of its own `sendAt`, never on the UTC date and never on the calendar day
  recorded beside it. It is the one case here that fails under a UTC-date bug AND under a
  trust-the-recorded-day bug. M2 is the mutation that exercises it.
- **17:00 AWST on the last day of a month — month-end enumeration, not the timezone guard.** 17:00
  AWST is 09:00Z on the same date and `planned.calendarDay` agrees with both, so every candidate
  derivation returns `2026-08-31` and the case fails under no plausible off-by-one. What it is
  actually worth is the month-end enumeration and its second assertion, that the following day holds
  nothing — a real distinction, since a day holding nothing and a day that was never asked about are
  different results. Kept for that, described as that.
- **A range across a month end.** Every day is enumerated, including the empty ones.

## Important 1 — two fields reached the wire unasserted

`messageType` and `planState` were mapped onto `ScheduleEntry` in `entryFor` and read by nothing.
Neither test file referenced `entry.messageType` or `entry.planState`, so both mappings were
type-compatible with a constant and no mutation in the ledger above targeted either — consistent
with there being no assertion to falsify. **This report did not disclose the gap**, which is the
worse half of it: a limitation nobody wrote down is not a limitation anybody weighed.

`messageType` is the field that matters most here. It is what tells a **closing message** apart from
a caring contact — a distinct kind, not one more contact — and the brief named that distinction
explicitly.

Two cases were added to `tests/caring-contacts-schedule-view.test.ts`, in a new block,
`buildScheduleRange — what an entry carries through from the planner and the plan`:

- **The message kind.** Each of a seeded plan's contacts is looked up on the AWST day it actually
  sends on — a plan runs for months and no single accepted range spans one — and the kinds reported
  are compared, contact by contact, against the kinds the planner stamped. Derived from the plan,
  never typed out. Two supporting lines: a labelled **fixture precondition** that the plan holds more
  than one kind, which is what stops the comparison being satisfiable by a constant, and a named
  assertion that the plan's last contact is the closing message and the read says so.
- **The plan state.** An active plan and a paused plan sit on the same day. Each entry's reported
  `planState` is compared against its own plan record's state, plan by plan so neither list's order
  is asserted, plus a labelled fixture precondition that the two states differ.

The plan-state case is the one worth understanding. `planHold` is derived from `record.plan.state`
**separately**, so it stayed correct under a hardcoded `planState` — the field went unnoticed
precisely because its more visible neighbour kept working. That is why the assertion compares the
raw state and not the hold.

## Important 2 — a false count inside the comment that explains a defensive branch

`schedule-view.ts`'s `notSendingReasonFor` ended with:

> `contactSendability` classifies exactly these four as `willNotBeSent`; if it ever classifies a
> fifth, saying nothing is better than naming the wrong reason.

comment names three. `absorbedByFirstContact` is not a `ContactState`, so no reading makes the
sentence true. This is the named failure mode of the standing discipline's writing rule — a count
restated in prose about something **elsewhere** — landing inside the very comment written to explain
a defensive branch, which is the same collision that rule already records having happened once.

**Not fixed by changing "four" to "three".** The sentence now states the invariant the branch rests
on, so adding a state cannot make it false:

> Unreachable while every state `contactSendability` answers `willNotBeSent` for is named above. If
> one is ever added there and not here, saying nothing is better than naming the wrong reason, so
> this returns null rather than guessing.

The same error was repeated in this report's M17 note ("one of the four the switch beneath it
names") and is corrected there in place, to "one of the states the switch beneath it names".

Nothing else in the file or the report was changed. In particular the `ScheduleNotSendingReason`
doc's "kept apart from the other three" is a count sitting **directly on top of the union it
counts**, which the discipline permits and which is correct.

## 1. The second "fixture precondition" was not one

As first written the line was:

```ts
expect(reported.get(active)).not.toBe(reported.get(paused));
```

`reported` is built from `allEntries(day)` — from `buildScheduleRange`'s output. So it read **the
code**, not the fixture, and it **does** go red under M20, where both sides become `"active"`. The
in-file label ("FIXTURE PRECONDITION, not a claim about the code") and Concern 3 ("cannot go red
under any mutation of `schedule-view.ts`") were both false of it. Precondition 1 was correctly
labelled: it reads planner records only.

The error was conservative — I under-claimed, so nothing was over-claimed and no coverage was
missing. That is not a defence. **A note saying "this cannot fail" on an assertion that can is
exactly what a later reader trusts and should not**, and it would have been read as licence to
delete the line during a future cleanup on the grounds that it proved nothing.

Fixed by taking the direct form, which reads the plan records rather than the output:

```ts
expect(new Set(records.map((record) => record.plan.state)).size).toBeGreaterThan(1);
```

The `active` and `paused` bindings became unused and were dropped with it, so the seeds are now bare
`await seedPlan(...)` calls.

**What this trades, stated rather than assumed.** The old line caught two different causes and could
not say which: a fixture that stopped seeding two states, and code that hardcoded one. The new line
catches only the first, unambiguously. Nothing is lost, because the second cause is already caught by
the assertion directly above it — and strictly so, not just in practice: if that assertion passes,
every plan's reported state equals its own record's state, and the records differ, so the reported
values must differ too. The old line could therefore only fail where the assertion above it had
already failed. **That is an argument, not a mutation** — M20 is consistent with it (only one
assertion error printed, so the line was never reached) but does not by itself establish it, and I
am not filing observed behaviour as proof of the general claim.

## 2. Two false counts about the Prettier evidence — inside the round that exists to remove a count

Round 2's gate row said "the five Task 12 source and test files" and Concern 1 said "two of five new
files". Neither number named a real set: Task 12 changed **seven** TypeScript files and created four
of them. Worse, the narrative's passing list named `src/lib/caring-contacts/model.ts`, which Task 12
never touched, while `src/app/api/caring-contacts/access-trail/route.ts`, which it did, had no
stated evidence under any reading of "the API route".

The substance survived — two files really were unformatted and really are repaired — but on a
**formatting** claim the set is the whole content of the claim. An evidence row that does not name
what it covers is not evidence.

Corrected by writing the set out: the file table now in "An unlisted finding" above lists every
TypeScript file Task 12 touched, whether it was new or edited, and its `prettier --check` verdict at
`6b75dcf3b`. The gate row points at that table instead of counting it, and Concern 1 names the two
failing files instead of giving a fraction.

**The rule this broke, in the sharper form the controller is putting into the standing discipline:**

> **The counts that rot are the ones about a set you are not looking at.** A count sitting directly
> on top of the list it counts has never failed here. Before writing a number, ask whether the thing
> it counts is **visible in the same view as the number**. If it is not, name the set instead of
> counting it.

My gate row was a count about files listed nowhere near it. That is the failing shape every time,
and this is the third occurrence in this programme — each one committed while removing somebody
else's instance of it, mine included. The older form of the rule ("do not restate a count in prose")
did not stop me, because I read my own row as a count "directly on top of" a list that was in fact
two sections away. The visible-in-the-same-view test would have.
